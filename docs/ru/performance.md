# Производительность и проверка воркера

[English](../performance.md)

Прямое сравнение с 3.0.0 приведено в отдельном [A/B-отчёте](../../benchmarks/compare-versions/results-2026-10-26.md):
20 000 документов, одинаковые зависимости, API/HTTP/очередь. Замеры ниже относятся только к 4.x.

INSERT/REPLACE билдера теперь подставляют конечные PHP float при построении SQL,
после преобразования по схеме. Числа внутри JSON остаются строковыми JSON-параметрами;
строки и остальные скалярные параметры по-прежнему передаются через PDO bindings.
Это относится также к `insertGetId()`, `replaceGetId()` и операциям, вызывающим эти методы.
В событиях запросов и query log float находится непосредственно в SQL, без отдельного
элемента в bindings. UPDATE, WHERE и raw SQL используют прежний `NumericBindings::prepare()`.
Результаты до и после изменения приведены в [повторном сравнении пакетной записи](../../benchmarks/profile-writes/optimized-results-2026-10-26.md).
В [анализе этапов SQL](../../benchmarks/sql-pipeline/results-2026-10-26.md) отдельно измерены
подготовка, вызовы PDO и повторное выполнение готовых запросов; проверены шесть гипотез
оптимизации и их совместимость. Отчёт описывает отдельные экспериментальные снимки;
реализованные изменения перечислены ниже.

Для INSERT/REPLACE из нескольких строк реализована специализированная подготовка
штатных `ManticoreQueryBuilder` и `ManticoreGrammar`. Значения проходят через прежний
`encodeWriteRows()`, затем фрагменты SQL и плоский массив bindings формируются совместно.
Колонки сортируются один раз; одинаковый порядок колонок повторно использует проверку
имён. Конечные скалярные float сразу становятся числовыми литералами, строки остаются
параметрами PDO. Для подклассов билдера/Grammar, пользовательских и вложенных Expression,
а также смены Grammar и регистрации callbacks при загрузке схемы сохранён прежний путь компиляции.
`cleanBindings()` выполняет один цикл с прежним `castBinding()` Laravel.
Одиночные строки и методы GetId используют существующий путь подготовки.

Результаты приведены в [сравнении реализованной пакетной подготовки](../../benchmarks/sql-pipeline/batch-writes.md).

Замеры ниже выполнены до специализированной пакетной подготовки, 26 октября 2026 года
на прежних исходниках 4.x: PHP CLI 8.3.6,
Laravel 12.70.1, Manticore 29.9.0 и Columnar/KNN 14.2.1. Один клиент подключался по
локальному TCP тестового сервера. Это результаты конкретного набора данных, без гарантий
пропускной способности или времени ответа других приложений.

В отдельной таблице было 5000 документов, после смешанного upsert — 5500. Каждый документ
содержал 128-мерный L2-вектор, stored TEXT и JSON с полезной нагрузкой 128 байт. Перед
проверкой hybrid HNSW-индекс построен через `FLUSH RAMCHUNK`. Query log отключён.

| Операция | Время | Дополнительный пик памяти PHP | Число SQL-запросов |
| --- | --- | --- | --- |
| INSERT 5000, порциями по 500 | 1,90 с | 8,77 МиБ | 11, включая получение схемы |
| Upsert 100 существующих строк | 0,30 с | 0,40 МиБ | 200 |
| Upsert 1000 существующих строк | 3,03 с | 2,76 МиБ | 2000 |
| Upsert 5000 существующих строк | 12,99 с | 13,90 МиБ | 10000 |
| Upsert 500 существующих + 500 новых | 3,18 с | 6,88 МиБ | 2000 |
| `get()`, все 5500 документов | 0,99 с | 21,25 МиБ | 1 |
| `cursor()`, все 5500 документов | 1,01 с | 8,97 МиБ | 1 |
| `lazy(250)`, все 5500 документов | 1,36 с | 1,95 МиБ | 23 |
| `chunkById(250)`, все 5500 документов | 1,29 с | 0,99 МиБ | 23 |

Upsert эмулируется: для каждой строки выполняются поиск и INSERT/REPLACE, все документы
замены подготавливаются до начала записи. Число запросов линейно, память зависит от размера
пакета. Это не один массовый SQL upsert. Используйте явные порции, например по 100–1000
строк, с учётом размера документов и допустимой длительности транзакции. Отдельные вызовы
получают отдельные транзакции, если приложение не создаёт внешнюю. Сетевая задержка
добавляется к каждому поиску и записи. Необновляемые поля существующих документов сохранены.

Cursor не хранит полную коллекцию, но PDO может буферизовать результат. Для меньшего пика
памяти по этим замерам подходят ограниченные порции `lazy()`/`chunkById()`. При обходе
проверены количество документов и сумма ID, включая последнюю неполную порцию.

| Кандидатов на каждую ветвь hybrid | Медиана / наблюдаемый p95 за 10 запусков | Максимальный дополнительный пик памяти |
| --- | --- | --- |
| 50 | 43,00 / 45,30 мс | 0,57 МиБ |
| 200 | 129,52 / 133,94 мс | 1,93 МиБ |
| 1000 | 365,58 / 421,26 мс | 8,85 МиБ |

Общий атрибутный фильтр сохранился в выдаче. Увеличение окна повышало время и память;
размер окна не становится точным total объединения всего корпуса.

После 100 прогревочных операций выполнены 1000 смешанных JSON/fulltext, facet и hybrid
операций за 16,63 с. Удерживаемая память выросла на 4544 байта, включая записи замеров;
выделенная память — на 0. Отдельный настоящий database queue worker обработал 120 заданий
по 15 операций без перезапуска. Между заданиями 20 и 120 прирост удерживаемой и выделенной
памяти составил 0. Задания включали JSON/fulltext, hybrid и upsert. Очередь опустела,
последняя запись проверена, исходные 2105 документов приложения и их отпечаток сохранены.
В этих конечных прогонах продолжающегося роста памяти не обнаружено.

## Как повторить

Нужны клон репозитория и autoload Laravel-приложения: его event dispatcher используется
для счётчика SQL. Основной скрипт создаёт и удаляет только случайную проверочную таблицу:

```sh
MANTICORE_TEST_HOST=127.0.0.1 MANTICORE_TEST_PORT=19306 \
MANTICORE_BENCHMARK_REPORT=/tmp/driver-benchmark.json \
php -d memory_limit=512M tests/benchmarks/native-driver.php /path/to/application/vendor/autoload.php
```

`MANTICORE_BENCHMARK_DIMS` принимает 3, 128 (по умолчанию) или 768. Для проверки воркера
поместите `tests/benchmarks/fixtures/DriverSoakProbe.php` в `app/Jobs/` тестового приложения
и выполните `php tests/benchmarks/laravel-worker.php /path/to/application`. Скрипт использует
соединение `manticore` приложения и отдельную database queue со случайными именами очереди
и таблицы. Нужны обычные таблицы очереди, CLI-обёртка `bin/php` либо её эквивалент и сервис
`Catalog` приложения проверки миграции для контроля сохранности данных. Полные JSON-замеры
сохранены в `storage/app/` приложения.
