# Исторический отчёт: реализация 3.x

Ниже сохранены прежние измерения и описание старых скриптов. Старый PHP-билдер и обёртка
удалены из 4.x; эти числа и команды не описывают текущий драйвер.
Актуальные скрипты и методика: [benchmarks 4.x](README.md).

# Замеры Manticore: MySQL-протокол против HTTP

Вопрос, ради которого всё затевалось: `avadim/manticore-query-builder-*` ходит в
Manticore по MySQL-протоколу через PDO (порт 9306), официальный
`manticoresoftware/manticoresearch-php` — по HTTP JSON (порт 9308). Считается,
что PDO поэтому быстрее. Замер проверяет, так ли это, и главное — сколько это
стоит на самом деле.

Короткий ответ: MySQL-протокол действительно быстрее HTTP, но **разница в
протоколе меньше, чем цена самого клиента**. Билдер съедает ровно столько же
(≈10%), сколько стоит переход на HTTP, так что на коротких запросах официальная
библиотека этому пакету не уступает. Дорого стоит не HTTP, а **формат**:
JSON-документы вместо текста SQL.

## Как устроено

Пять клиентов, одни и те же данные, одна и та же схема таблицы:

| Обозначение | Клиент | Протокол | Формат |
|---|---|---|---|
| `PDO` | голый PDO | MySQL, 9306 | SQL |
| `QB` | `avadim/manticore-query-builder-php` | MySQL, 9306 | SQL |
| `QB+Laravel` | тот же билдер с `Connection` этого пакета | MySQL, 9306 | SQL |
| `HTTP SQL` | официальный клиент, `Client::sql($sql, true)` | HTTP, 9308 | SQL |
| `HTTP JSON` | официальный клиент, `/bulk` и `/search` | HTTP, 9308 | JSON |

Смысл в паре `HTTP SQL` / `HTTP JSON`: они отличаются только форматом при одном
транспорте, а `HTTP SQL` и `PDO` — только транспортом при одном формате. Это
позволяет вычесть одно из другого, а не гадать, что именно замедлило.

`QB+Laravel` — это `Laravel\Query`, отдающий `Collection` из `Row` вместо
массивов. Он включается тем же `Builder::setConnectionClass()`, что и в
`ServiceProvider::boot()`, поэтому приложение Laravel для замера не нужно.

Документы генерируются (`benchDocuments()` в `shared.php`), а не читаются из
чужой базы: замер должен запускаться в этом репозитории. Генератор
детерминированный, все клиенты получают одни и те же документы. Названия — смесь
русских и английских слов, таблица создаётся с `lemmatize_ru_all,
lemmatize_en_all` и `min_infix_len=3`, чтобы сервер работал по-настоящему.

## Запуск

```sh
cd benchmarks && composer install && cd ..

php -d xdebug.mode=off benchmarks/manticore_insert_pdo.php       200000 500
php -d xdebug.mode=off benchmarks/manticore_insert_qb.php        200000 500
php -d xdebug.mode=off benchmarks/manticore_insert_http_sql.php  200000 500
php -d xdebug.mode=off benchmarks/manticore_insert_http_json.php 200000 500
php -d xdebug.mode=off benchmarks/manticore_search_bench.php     2000 200000
```

Нужен живой демон на 9306 **и** 9308. Адреса — `MANTICORE_TEST_HOST`,
`MANTICORE_TEST_PORT`, `MANTICORE_TEST_HTTP_PORT`.

`-d xdebug.mode=off` здесь не косметика, а обязательное условие — см. последний
раздел.

## Вставка

200 000 документов, пачка 500. Медиана трёх прогонов.

| | PDO | QB | HTTP SQL | HTTP JSON |
|---|---:|---:|---:|---:|
| Подготовка, с | 0,36 | 0,77 | 0,43 | 0,56 |
| Обмен (сеть + сервер), с | 5,37 | 5,51 | 5,82 | 8,86 |
| **Итого, с** | **5,70** | **6,30** | **6,25** | **9,39** |
| Документов в секунду | 35 094 | 31 458 | 32 021 | 21 099 |
| Против PDO | — | +10,6% | +9,6% | +64,7% |

Отсюда всё и раскладывается:

- **Транспорт** (`HTTP SQL` против `PDO`, формат одинаковый): **+9,6%**. Столько
  стоит HTTP по сравнению с MySQL-протоколом.
- **Формат** (`HTTP JSON` против `HTTP SQL`, транспорт одинаковый): **+50%**.
  Столько стоит JSON по сравнению с текстом SQL.
- **Билдер** (`QB` против `PDO`): **+10,6%** — то есть примерно столько же,
  сколько стоит весь переход на HTTP.

Формат дороже транспорта впятеро. Разница в пачке из 500 документов: SQL — один
`REPLACE INTO ... VALUES (...), (...)`, где имена колонок написаны один раз;
JSON — 500 отдельных объектов, в каждом повторены все одиннадцать имён полей.
Их надо сериализовать на клиенте и разобрать на сервере, и это видно в столбце
«обмен»: 8,86 с против 5,4–5,8 с у всех остальных.

## Чтение

Индекс 200 000 документов, 2000 запросов на профиль, медиана трёх прогонов.
Медиана задержки одного запроса, мс:

| Профиль | PDO | QB | QB+Laravel | HTTP SQL | HTTP JSON | демон |
|---|---:|---:|---:|---:|---:|---:|
| точечный — `MATCH`, `LIMIT 20` | 2,73 | 3,10 | 3,29 | 3,21 | 3,18 | ~1 |
| ранжирование — то же + `ORDER BY` | 2,57 | 2,88 | 2,81 | 2,74 | 2,57 | ~1 |
| объём — `MATCH`, `LIMIT 1000` | 17,27 | 20,25 | 20,05 | 22,58 | 23,34 | ~14 |

Против PDO:

| Профиль | QB | QB+Laravel | HTTP SQL | HTTP JSON |
|---|---:|---:|---:|---:|
| точечный | +14% | +21% | +17% | +16% |
| ранжирование | +12% | +9% | +7% | −0% |
| объём | +17% | +16% | +31% | +35% |

Что из этого следует:

- **На коротких запросах все пятеро в пределах полумиллисекунды друг от друга.**
  Официальный HTTP-клиент не медленнее билдера этого пакета: 3,18 против 3,10 мс
  на точечном профиле и 2,57 против 2,88 на ранжировании — то есть на
  ранжировании он билдер обгоняет. Предположение «PDO быстрее, значит этот пакет
  быстрее официальной библиотеки» на этом профиле не подтверждается.
- **На объёмной выдаче MySQL-протокол выигрывает по-настоящему** — 17,3 против
  22,6–23,3 мс. Тысяча строк по HTTP означает сериализацию всего результата в
  JSON на сервере и `json_decode` на клиенте; `mysqlnd` отдаёт то же самое
  дешевле. Билдер здесь посередине (20,2 мс): он платит за разбор ответа, но
  сохраняет преимущество транспорта.
- **Обёртка для Laravel почти бесплатна.** `Collection` из `Row` вместо массивов
  стоит от −4% до +7% — это на уровне разброса между прогонами. Тысяча объектов
  `Row` на объёмном профиле не стоила ничего заметного.
- **Чем больше работы у демона, тем меньше значит клиент.** На объёмном профиле
  из 17–23 мс около 14 приходится на сам сервер (`took` из HTTP-ответа), и
  вся разница между клиентами укладывается в остаток.

Про `took`: это единственная сопоставимая оценка серверного времени, которая
здесь есть. У SQL такой нет — `SHOW META` отдаёт время поиска и не считает
формирование ответа, поэтому на объёмном профиле показывает сотые доли
миллисекунды там, где `took` даёт четырнадцать. Ставить эти два числа рядом
нельзя, поэтому в таблице одно.

## Вывод

Предположение верное по направлению и сильно завышенное по величине.

- Протокол: MySQL быстрее HTTP на 10% на вставке, на 15–17% на точечных
  запросах и на ~30% на объёмной выдаче.
- Но пакет — это не голый PDO. Билдер тратит примерно столько же, сколько
  стоит HTTP, и на коротких запросах преимущество протокола он проедает целиком.
- Реальное преимущество остаётся там, где много данных: массовая вставка (билдер
  на треть быстрее официального клиента с JSON — 6,3 против 9,4 с) и объёмная
  выдача (20,2 против 23,3 мс).
- Выбирать библиотеку по протоколу не стоит: на типичном поиске с `LIMIT 20`
  разница между всеми пятью клиентами — доли миллисекунды при работе демона в
  1 мс. Выбирать стоит по API.

## Отдельно: Xdebug искажает такие замеры в разы

Первая редакция этого замера (на данных каталога) давала билдеру 133 мкс на
документ подготовки против 3,9 мкс у голого PDO и вывод «билдер медленнее в
5,4 раза, 82% времени — клиентские». Это оказался артефакт: `xdebug.mode` на
машине по умолчанию `develop,debug`, а тот прогон шёл без `-d xdebug.mode=off`.

Сверка на нынешних скриптах, 5000 документов:

| | подготовка, мкс/док | док./с |
|---|---:|---:|
| билдер без Xdebug | 3,0 | 31 236 |
| билдер с Xdebug | 126,0 | 6 425 |
| голый PDO без Xdebug | 1,0 | 34 893 |
| голый PDO с Xdebug | 2,8 | 29 571 |

Числа с Xdebug совпали со старым замером почти точно (126 против 133 мкс,
6 425 против 6 144 док./с) — сомнений в причине не осталось.

Xdebug берёт плату за каждый вызов функции. Голый PDO делает на документ один
`sprintf` и три `quote`, поэтому почти не замечает; билдер обходит колонки,
сверяется со схемой и приводит типы — десятки вызовов на документ, и он
замедляется в сорок раз. Время сервера при этом не меняется вовсе, из-за чего
и получается убедительная картина «клиент виноват, сервер ни при чём».

Практический вывод: **любой замер здесь запускать только с
`-d xdebug.mode=off`**, а вывод «библиотека медленная» перепроверять этим
ключом прежде всего остального. Реальная цена билдера — не пятикратная, а
около 10%.
