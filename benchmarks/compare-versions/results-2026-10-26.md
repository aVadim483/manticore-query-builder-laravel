# A/B: библиотека 3.0.0 против 4.0.0

Замер выполнен 26 октября 2026 года на одном сервере и одинаковом наборе **20 000 документов**: stored TEXT, JSON с нагрузкой 128 байт, MVA и 128-мерный L2 HNSW. Индекс построен до измерений. Публичное приложение оставалось на 4.0.0.

PHP CLI **8.3.6**, Laravel **12.70.1**, Manticore **29.9.0**, Columnar/KNN **14.2.1**, локальный TCP. Все **77 общих Composer-пакетов** имеют одинаковые версии и source references. В 3.x дополнительно установлен PHP-билдер 2.6.0. Xdebug отсутствует, query log отключён, PDO emulated prepares и buffered queries одинаково включены.

Результат зависит от операции. Постраничный обход в 4.0 быстрее примерно на 23%, HTTP практически не изменился. При одинаковом получении метаданных большинство поисков близки; KNN медленнее примерно на 23%. Пакетные INSERT/REPLACE на этом наборе требуют примерно в 1,62 раза больше времени в 4.0.

Количество SQL означает вызовы PDO, включая SHOW META и получение последнего ID. У 3.x обычный get() получает META; поэтому отдельная строка rows-only сравнивает getRows() 3.x с get() 4.x. Для поиска с META обе версии выполняют два вызова. При INSERT/REPLACE 3.x дополнительно запрашивает LAST_INSERT_ID().

Пять полных обходов и десять операций записи дают ограниченную выборку; p95 для таких выборок совпадает с наблюдавшимся максимумом. Нативный cursor() 4.x выполняет один SELECT и не является старым постраничным cursor(500); коэффициент между ними намеренно не рассчитан.

## HTTP и задания очереди

HTTP измерен через Laravel на двух закрытых PHP built-in серверах с одинаковым PHP и opcache.enable_cli=1: по 20 прогревочных и 50 измеряемых запросов, версии чередуются. Это время всего HTTP-запроса с bootstrap, соединением, DTO и JSON. PDO-инструментация отключена; число SQL и память HTTP не измерялись. Это не нагрузочный замер PHP-FPM.

| JSON/MVA/128d, 1000 строк | 321.117 / 326.312 | 318.428 / 325.693 | -0.8% |

Настоящий database queue worker: четыре серии по 12 заданий на версию, первые два задания каждой серии прогревочные. В итог вошли 40 заданий на версию. Одно задание выполняет 15 поисков с проверкой DTO; время ожидания и запуск воркера исключены. Медиана / p95: **46.549 / 48.312 мс** на 3.x и **50.206 / 53.122 мс** на 4.x (+7.9%). PDO-вызовов на задание: 30 / 25. Воркеры перезапускались между сериями; это не длительный soak-тест.

## Корректность и границы выводов

Все хеши нормализованных результатов совпали: строки и порядок, JSON/MVA/векторы, метаданные, фасеты, подсветка и состояние таблиц после записи. Float нормализованы до шести знаков после запятой. При обходах совпали количество, сумма и SHA-256 последовательности всех ID. HTTP-ответы совпали побайтово, результаты заданий очереди также совпали. Ошибки корректности останавливают сценарий.

Все проверочные таблицы удалены, HTTP-серверы и воркеры остановлены, отдельные очереди и failed_jobs пусты. Публичное приложение осталось на 4.0.0, все 2105 исходных документов и их отпечаток сохранены.

Разницу в 1–5% на коротких запросах следует трактовать как близкие результаты этого прогона. Общего ускорения всех операций нет. Пакетная запись и KNN — конкретные кандидаты для отдельного профилирования; данный замер не устанавливает, какая функция создаёт накладные расходы. Уменьшение числа SQL само по себе не гарантирует сокращения общего времени.

PDO не выполняет все преобразования моделей и типов библиотек. Его API-время даёт контрольную точку транспорта/сервера, а не полностью эквивалентную готовую прикладную выдачу. Нормализация результатов записана отдельно в исходных данных. Hybrid и upsert 4.x не сравниваются с несуществующими одноимёнными возможностями 3.x.
