# Сравнение 3.0.0 и 4.0.0

Сценарии запускаются **на хосте Manticore** с двумя закрытыми Laravel-приложениями:
одним с опубликованной библиотекой 3.0.0 и PHP-билдером 2.6.0, другим с опубликованной
4.0.0. Версии PHP, Laravel и остальных общих Composer-зависимостей должны совпадать.
Публичное приложение для измерения не переключается.

```sh
python3 benchmarks/compare-versions/run.py \
  --v3 /path/to/private-v3-app \
  --v4 /path/to/private-v4-app \
  --output /tmp/manticore-ab-results.json
```

Требуются PHP 8.2+, Python 3, PDO MySQL, готовые таблицы Laravel database queue в отдельных
SQLite-базах и исполняемая CLI-обёртка `bin/php` в каждой копии приложения. Соединения обеих
версий должны указывать на `127.0.0.1:19306` с пустым префиксом. Для другого адреса измените
PDO DSN в адаптере и настройки обеих копий. Отключите прикладные обработчики логирования
запросов в этих копиях; приложение не должно обслуживать пользовательский трафик.

Скрипт создаёт четыре таблицы со случайным префиксом `abcmp_*`: общий read-only набор и
три независимые таблицы записи. Они удаляются в `finally`. Схема, документы, фильтры, поля,
порядок и вектор запроса одинаковы. Запись и восстановление тестовых данных выполняются
через контрольный PDO вне измеряемого участка. Сценарии не обращаются к таблицам приложения.

По умолчанию создаются 20 000 документов, в том числе stored TEXT, JSON, MVA и HNSW L2
на 128 измерений. Перед чтением выполняется `FLUSH RAMCHUNK`. Вариант для предварительной
проверки: `--documents 2000 --read-samples 5 --skip-http-queue`.

## Методика

* Для прямых API-сценариев работают три постоянных PHP-процесса: 3.x, 4.x и контрольный PDO.
  Клиенты выполняются последовательно; первым становится очередной клиент по кругу.
* На каждый сценарий даются три прогревочных запуска. Чтения измеряются 100 раз, запись —
  10 раз, полные обходы — 5 раз. Подключение, подготовка схемы и начальное наполнение исключены.
* API-время включает построение запроса, выполнение SQL, получение строк и стандартные
  преобразования типов библиотек. Преобразование в контрольный DTO, вычисление SHA-256
  и проверочное чтение после записи выполняются отдельно и не входят в API-время.
* `get()` сравнивается как привычный вызов: 3.x также получает `SHOW META`. Для одинаковой
  работы отдельно сравниваются `getRows()` 3.x с `get()` 4.x и чтения с метаданными в обеих версиях.
* Старый `cursor(500)` сравнивается с постраничным `lazy(500)` 4.x. Нативный `cursor()` 4.x
  вынесен в отдельную строку без коэффициента сравнения с 3.x.
* Проверяются полные хеши нормализованных результатов, включая порядок ID, JSON/MVA/векторы,
  метаданные, фасеты, подсветку и данные после записи. Для обходов — количество, сумма и хеш
  всех ID. Несовпадение останавливает измерение, а не попадает в итоговую таблицу.

Для счётчика SQL используется один PDO-подкласс, учитывающий подготовленные statement,
прямые `query()` и `exec()`, включая `SHOW META` и чтение последнего ID. Он сохраняет
параметры fetch, эмуляции, буферизации и ошибок исходного PDO; установка выполняется до прогрева.
В 3.x доступ к существующему
приватному PDOClient нужен только для подключения этой инструментации. Vendor не редактируется.
Число запросов — вызовы PDO, а не внутренние серверные вычисления FACET.

## HTTP и очередь

Во временных копиях создаются только benchmark-маршрут и класс задания. Два PHP built-in
сервера слушают случайные порты **только 127.0.0.1**. Измеряются настоящие HTTP-запросы
через Laravel с одинаковым CLI PHP и `opcache.enable_cli=1`: 20 прогревочных, затем 50 запросов
на версию и сценарий с чередованием версий. Ответы сравниваются побайтово. PDO-инструментация
для HTTP отключена; измеряется весь запрос, включая bootstrap, соединение, DTO и JSON.
Это сравнение закрытых CLI-серверов, а не замер производственного PHP-FPM.

Для очереди выполняются четыре серии на версию с порядком 3→4, 4→3, 3→4, 4→3. В каждой
серии настоящий `artisan queue:work` обрабатывает 12 заданий, первые два прогревочные.
Каждое задание выполняет 15 операций: MATCH с метаданными, JSON/MVA и KNN с контролем DTO.
В итог идут 40 заданий на версию. Это время обработчика задания; ожидание в очереди и запуск
воркера не входят в него. Воркеры между сериями перезапускаются, что явно отражено в методике;
это не длительный soak-тест одного процесса. Очереди имеют случайные имена и отдельные базы.

Полный JSON сохраняет исходные выборки времени, памяти и числа запросов, результаты прогрева
с примерами SQL, хеши и окружение. Медиана и p95 описывают данный прогон без обещаний для
других размеров документов, серверов и сетевой задержки. Память указана как полный пик
используемой PHP-памяти, включая Laravel; это не RSS ОС. Скрипт не настраивает MySQL,
не меняет публичный сайт и не требует установки HTTP-клиента.

## Сохранённый прогон

[Результаты 26 октября 2026](results-2026-10-26.md) содержат таблицы медиан, p95 и памяти.
Рядом сохранены сводный JSON и полный JSON gzip с отдельными измерениями и хешами.
Восстановить именно этот зафиксированный отчёт можно командой:

```sh
node benchmarks/compare-versions/render-recorded-report.cjs \
  benchmarks/compare-versions/results-2026-10-26.raw.json.gz /tmp/report-rebuild
```

Генератор проверяет SHA-256 сохранённого снимка. Новые прогоны `run.py` получают собственные
JSON и консольные сводки; исторический отчёт ими не перезаписывается.
